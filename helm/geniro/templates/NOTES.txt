=== Zitadel Post-Install (Required) ===

Zitadel generates OIDC client IDs dynamically at first boot.
After the Zitadel pod is Ready, complete setup:

1. Port-forward Zitadel:
   kubectl port-forward svc/{{ .Release.Name }}-zitadel 8080:8080 -n {{ .Release.Namespace }}

2. Log in at http://localhost:8080 with your FirstInstance admin credentials.

3. Create an OIDC application for Geniro (or use the one created by init).
   Copy the generated Client ID.

4. Upgrade the release with the client ID:
   helm upgrade {{ .Release.Name }} ./helm/geniro \
     --reuse-values \
     --set api.env.zitadelClientId=<CLIENT_ID> \
     --set api.env.authProvider=zitadel

{{- end }}

=== Important Notes ===

1. CREDENTIAL_ENCRYPTION_KEY: This key encrypts all stored credentials (GitHub PATs,
   API keys, etc.). Back it up securely. If lost, all stored credentials become
   unrecoverable.

2. Frontend Config: The Web image has API_URL compiled in at build time via
   geniro-web/src/config/production.ts. If you are using custom domains, you must
   edit production.ts and rebuild the web image before deploying.

3. Docker Socket: By default, the API does NOT mount the host Docker socket
   (api.mountDockerSocket=false). To enable Docker-based tool execution, set
   api.mountDockerSocket=true. Alternatively, deploy the Daytona sandbox runtime
   (daytona.enabled=true) for isolated container execution without a host socket.

4. Ingress Controller: If you enabled ingress, ensure an ingress controller
   (e.g., ingress-nginx) is installed in your cluster.

{{- if .Values.daytona.enabled }}

SECURITY NOTE: The Daytona runner API key is stored in a ConfigMap (nginx limitation).
  nginx cannot natively reference Kubernetes Secrets for header values.
  For production: enable etcd encryption at rest and restrict ConfigMap RBAC access
  in the {{ .Release.Namespace }} namespace. Apply least-privilege RBAC so that only
  the Daytona proxy ServiceAccount (and cluster admins) can read ConfigMaps.
{{- end }}
